# 프로젝트 파일 포맷

`@cp949/projectfile`이 만들고 여는 프로젝트 파일의 포맷과 검사 규칙이다. 이 문서가 규칙의 원천이다.

- 구현은 `packages/projectfile/src`에 있다.
- 설치, 사용 예, `rules`, `limits`, 실패 이유 표는 `packages/projectfile/README.md`에 있다.
- 파일 트리, 화면, 서버 저장 같은 소비자의 규칙은 이 문서에 없다.

## 경계

라이브러리는 바이트와 항목(`ProjectEntry`)만 안다.

- 파일 트리, 화면, 에디터를 모른다.
- 브라우저와 Node에서 돈다. `Blob`, `Response`, `TextEncoder`, `TextDecoder` 전역을 쓴다.
- 의존은 `fflate` 하나다.
- 공개 API는 `src/index.ts`가 전부다. `scramble`, `zip`, `crc32` 같은 내부 모듈은 내보내지 않는다.
- `exports`는 `dist`를 가리킨다. 소비하기 전에 빌드가 필요하다.
- 입력은 `Blob` 또는 `Uint8Array`다. 인코딩 출력은 `application/octet-stream` `Blob`이다(`PROJECT_FILE_MIME`).

호출자가 모르는 정책을 주입한다.

- `rules`(`ProjectFileRules`):
  - `maxPathLength`: 항목 경로의 최대 길이. 1 이상 `MAX_PATH_LENGTH_CEILING`(1,024) 이하의 정수여야 한다.
  - `checkSegment`: 경로 조각 하나의 이름 규칙. 확장자나 조각 길이가 여기에 든다. 비워도 된다.
  - `isCode`: 코드 한도에 세는 텍스트인지.
- `limits`(`ProjectFileLimits`): 모든 항목을 호출자가 넘긴다. 기본값이 없다. 항목은 0 이상의 정수여야 한다.
- `kind`: 파일의 종류. 사용처가 정한다("kind").
- scramble 키: 비우면 기본 키를 쓴다("scramble 키").
- scramble 범위(`scrambleScope`): 인코딩 옵션. 비우면 `"metadata"`다("scramble").

오류는 두 갈래다.

- 열 수 없는 파일은 던지지 않는다. `ProjectFileFailure`를 돌려준다. 사용자가 고른 파일이 틀릴 수 있다. `Blob`을 읽지 못한 경우(`read-failed`)도 같다.
  - 디코딩은 입력 `Blob`을 읽지 못하면 `read-failed`를 돌려준다. `path`가 없다.
  - 인코딩은 asset `Blob`을 읽지 못하면 `read-failed`와 그 asset의 `path`를 돌려준다.
- 호출자 버그는 던진다.
  - 규칙을 어긴 `kind`.
  - 길이가 16이 아닌 scramble 키.
  - `"metadata"`나 `"all"`이 아닌 `scrambleScope`.
  - 빈 `scrambleKeys`, 키 확인값이 같은 키가 둘 이상인 `scrambleKeys`.
  - 잘못된 `maxPathLength`와 한도 항목. NaN이나 음수는 검사를 조용히 없애기 때문이다.
  - 절대 상한(`MAX_UNCOMPRESSED_BYTES_CEILING`)을 넘는 `maxUncompressedBytes`("한도").
  - `maxFiles` + `maxFolders` + 2가 `MAX_ZIP_ENTRIES`를 넘는 한도("한도").

## 헤더

헤더는 scramble하지 않는다. 길이는 22 + N바이트다. N은 kind 문자열의 길이다.

| 위치     | 내용                                                      |
| -------- | --------------------------------------------------------- |
| 0..3     | magic `OCOD` (`0x4f 0x43 0x4f 0x44`)                      |
| 4        | 포맷 버전. 1 또는 2                                       |
| 5        | kind 길이 N. 1 이상 64 이하                               |
| 6..9     | payload 길이. LE uint32. payload는 ZIP 전체다.            |
| 10..13   | CRC32. LE uint32. 범위는 "scramble"                       |
| 14..17   | `centralStart`. ZIP 안 중앙 디렉터리 시작 위치. LE uint32 |
| 18..21   | 키 확인값. 키 16바이트의 CRC32. LE uint32                 |
| 22..21+N | kind 문자열. ASCII                                        |
| 22+N..   | payload = scramble한 ZIP. 버전 1은 일부, 버전 2는 전체    |

- 헤더 길이의 최대는 86바이트다(`MAX_HEADER_BYTES`, `src/header.ts`).
- 파일 크기는 22 + N + payload 길이와 같아야 한다.
- 키가 없는 쪽도 헤더만으로 magic, 버전, kind, 길이, 키 확인값을 읽을 수 있다.
- CRC는 scramble 전 평문 기준이라 키 없이 계산할 수 없다. 클라이언트가 열 때 검사한다.
- 포맷 버전은 scramble하는 범위를 정한다. 이 값이 파일에 남는 유일한 표시이므로 디코딩은 버전을 보고 범위를 안다.
  - 버전 1: ZIP 메타데이터 범위와 `manifest.json` 본문만 섞는다.
  - 버전 2: ZIP 전체를 섞는다. 헤더 CRC도 ZIP 전체를 본다.
- 1과 2가 아닌 버전은 열지 않고 `unsupported-version`으로 거부한다.
- 두 버전의 헤더 배치는 같다. 서버가 헤더만 읽는 구현은 버전 값 2를 받아야 한다.
- ZIP 메타데이터가 섞여 일반 압축 도구가 파일 목록을 읽지 못한다.
- 로컬 헤더, 중앙 디렉터리, `manifest.json` 본문이 섞인다. 시그니처와 모든 파일 경로가 평문으로 보이지 않는다.
- 버전 1은 섞지 않는 텍스트와 asset 본문에 평문이 남는 경우가 있다("ZIP과 manifest"). 버전 2는 남지 않는다.
- 두 버전의 선택 이유와 대안은 `docs/adr/0007-full-scramble-version.md`에 있다.

### kind

kind는 사용처가 정하는 문자열이다. 라이브러리는 kind 목록을 갖지 않는다.

- 규칙은 정규식 `^[a-z0-9][a-z0-9._-]{0,63}$`다. 길이는 1 이상 64 이하다. 대문자를 받지 않는다.
- 정규식은 문자열 전체와 일치해야 한다. 끝 줄바꿈(`0x0a`)도 받지 않는다. 어떤 정규식 엔진은 `$`가 끝 줄바꿈 앞에서도 맞으므로 다른 언어 구현은 전체 일치 함수를 쓴다.
- 비교는 완전 일치다.
- 인코딩·디코딩 옵션의 `kind`가 규칙을 어기면 던진다.
- 파일 헤더의 kind가 규칙을 어기면 `kind-invalid`다. 헤더의 kind 길이 N이 0이거나 64를 넘는 경우도 같다.
- 디코딩은 규칙을 지킨 헤더 kind가 옵션의 `kind`와 다르면 `kind-mismatch`다. 규칙 검사가 먼저다.
- manifest의 kind 형식이 틀리면(규칙 위반 포함) `manifest-invalid`다. 헤더 kind와 다르면 `manifest-kind-mismatch`다.
- kind 문자열은 와이어 포맷 값이다. 헤더의 읽기·쓰기는 `src/header.ts`가 소유한다.

## ZIP과 manifest

ZIP은 표준 ZIP이다. 파일은 메타데이터 범위가 섞여 있어 복원해야 표준 ZIP이 된다. 항목은 세 종류다.

- `manifest.json`: 메타.
- `files/<경로>`: 파일 내용.
- `files/<경로>/`: 폴더. 빈 폴더도 담는다. `files/` 폴더 항목도 있다.

manifest 필드:

| 필드            | 내용                                                           |
| --------------- | -------------------------------------------------------------- |
| `formatVersion` | 헤더 버전과 같아야 한다.                                       |
| `kind`          | kind 규칙을 지키는 문자열. 헤더 kind와 같아야 한다.            |
| `files`         | 파일마다 `path`(`files/`를 뗀 경로)와 `type`(`text`, `asset`). |

- `files`의 순서가 디코딩 출력 항목의 순서다.
- `path`가 겹치면 거부한다. 추가 필드는 버린다.
- manifest 본문은 UTF-8이다. 올바른 UTF-8이 아니면 `manifest-invalid`다. UTF-16 BOM(`FF FE`, `FE FF`)으로 시작하는 본문은 올바른 UTF-8이 아니다.
- manifest 본문 맨 앞의 UTF-8 BOM(`EF BB BF`) 하나는 무시하고 JSON으로 읽는다.
- 그 BOM 말고 JSON 문자열 밖에 U+FEFF가 있으면 `manifest-invalid`다. 둘째 BOM, JSON 중간과 끝의 U+FEFF가 그렇다. U+FEFF는 JSON 공백이 아니다.
- JSON 문자열 안의 U+FEFF는 JSON이 허용하므로 값의 일부다. 경로에 들어 있으면 경로의 일부로 읽는다.
- 경로 조각의 앞이나 뒤에 있는 U+FEFF는 앞뒤 공백이다. `invalid-char`다("이름 규칙").
- 인코딩은 manifest 본문 앞에 BOM을 쓰지 않는다.
- `entry`는 없다. 진입 파일은 호출자가 정한다.
- 노드 종류가 필요하다. ZIP 항목만으로 텍스트와 asset을 가를 수 없다. 확장자로 가르면 큰 텍스트가 asset으로 바뀐다.
- 폴더는 manifest에 적지 않는다. ZIP 폴더 항목이 담는다.
- 내용을 `files/` 아래에 두는 이유: 사용자 파일 `manifest.json`과 이름이 겹치지 않는다.
- 항목은 `manifest.json`, `files/` 폴더 항목, `files/` 아래 폴더 항목, manifest가 적은 파일뿐이다. 그 밖의 항목과 manifest에만 있는 파일은 거부한다.
- 텍스트는 UTF-8로 deflate한다. asset은 압축하지 않는다. 이미 압축된 형식이 많아 CPU만 쓴다.
- 텍스트 본문의 짝 없는 서로게이트는 UTF-8 인코딩에서 U+FFFD가 된다. 인코딩은 거부하지 않는다. 경로의 짝 없는 서로게이트는 `invalid-char`다("이름 규칙").
- asset을 압축하지 않으므로 ZIP 안의 asset 본문 범위가 원본 바이트다. 디코딩이 이 범위를 `Blob`으로 돌려준다.
- ZIP 필드와 항목 순서를 고정한다. 같은 입력은 같은 바이트가 된다.

섞지 않는 본문에 평문이 남는 경우(버전 1만. 버전 2는 모든 본문을 섞는다):

- deflate는 블록마다 stored, 고정 Huffman, 동적 Huffman 중 짧은 것을 고른다.
- stored 블록은 입력 바이트를 그대로 담는다.
- ASCII 바이트는 고정 Huffman 부호가 8비트다. stored 블록이 더 짧지 않아서 ASCII만 있는 텍스트는 평문으로 남지 않는다.
- 비 ASCII가 많고 반복이 적은 짧은 텍스트는 stored 블록이 될 수 있다. 이때 텍스트 내용이 평문으로 남는다.
- asset 본문은 원본 그대로다. ZIP 형식 asset이면 그 안의 시그니처도 보인다.
- `manifest.json`도 같은 규칙으로 deflate한다. 비 ASCII 이름이 많은 짧은 manifest는 stored 블록이 되어 이름이 평문으로 남는다. 테스트가 무작위 한글 음절 30자 이름으로 이 경우를 만든다.
- manifest에는 모든 파일 경로가 있다. 그래서 manifest 본문을 섞는다.

### ZIP 쓰기

인코딩이 쓰는 ZIP의 필드다.

- 일반 목적 플래그는 `0x0800`(비트 11, 이름이 UTF-8)이다. 로컬 헤더와 중앙 디렉터리가 같다.
- DOS 시각은 0이고 DOS 날짜는 `0x0021`(1980-01-01)이다.
- 로컬 헤더의 extra 길이는 0이다.
- 중앙 디렉터리 항목의 extra 길이와 comment 길이는 0이다.
- 중앙 디렉터리 항목의 시작 디스크 번호, 내부 속성, 외부 속성은 0이다.
- 끝 레코드의 디스크 번호 두 개는 0이다.
- 끝 레코드의 ZIP 주석 길이는 0이다.
- ZIP64를 쓰지 않는다.
- 만든 버전과 필요한 버전은 20이다.
- 압축 방식은 항목 종류가 정한다.

| 항목            | 압축 방식  | 본문          |
| --------------- | ---------- | ------------- |
| `manifest.json` | deflate(8) | manifest JSON |
| 텍스트          | deflate(8) | UTF-8 텍스트  |
| asset           | 저장(0)    | 원본 바이트   |
| 폴더            | 저장(0)    | 비어 있다     |

- deflate는 fflate `deflateSync`의 기본 수준이다.
- asset 항목의 CRC32는 `Blob`을 조각으로 읽어 이어서 계산한다.

### 항목 순서

인코딩이 ZIP 항목을 쓰는 순서다.

1. `manifest.json`.
2. `files/` 폴더 항목.
3. `files/` 아래 항목. 폴더 트리의 전위 순회다.
   - 폴더는 자기 항목을 쓴 뒤 그 안의 항목을 쓴다.
   - 한 폴더 안에서는 하위 폴더가 파일보다 먼저다.
   - 하위 폴더는 처음 나온 순서다. 인코딩 옵션 `folders`가 먼저고 `entries`의 조상 폴더가 그 뒤다.
   - 파일은 `entries` 순서다.

- 디코딩은 ZIP 항목 순서를 검사하지 않는다.
- 디코딩 출력의 `entries`는 manifest 순서이고 `folders`는 중앙 디렉터리 순서다. 인코더가 만든 파일은 위 순서와 같다.

## scramble

- 목적은 인라인 검사 장비의 오탐을 피하는 것이다. 압축 유틸리티가 파일 목록을 읽지 못하게 한다. 암호가 아니다. 결정은 `docs/adr/0006-no-confidentiality.md`에 있다.
- 복원 규칙이 코드에 있어 분석하면 풀 수 있다. 기밀성과 변조 방지를 약속하지 않는다.
- 바이트마다 `치환표[바이트 ^ 키스트림(위치)]`다. 출력은 입력 바이트와 위치만 따른다.
- 입력을 나눠 처리해도 한 번에 처리한 결과와 같다. 나눈 조각의 시작 위치를 `offset`으로 넘긴다. 범위마다 섞는 데 쓰는 성질이다.
- 블록 순서 섞기는 쓰지 않는다. 전체 버퍼링이 필요해 스트리밍과 충돌한다.
- 동기 처리다. Web Worker와 `ReadableStream` 같은 스트리밍은 쓰지 않는다.
- 버전 2는 `Blob`을 1 MiB(`CHUNK_BYTES`)씩 읽는다. 조각마다 계산은 동기다.

섞는 범위와 CRC 범위:

| 항목      | 버전 1                                                                                                    | 버전 2                                                            |
| --------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 섞는 범위 | 항목마다 로컬 헤더, `manifest.json` 항목의 본문, `centralStart`부터 ZIP 끝까지(중앙 디렉터리 + 끝 레코드) | ZIP 전체                                                          |
| 본문      | manifest만 섞는다. 나머지 텍스트(deflate)와 asset(원본)은 섞지 않는다                                     | 모든 본문을 섞는다                                                |
| CRC 범위  | scramble 전 평문의 섞는 범위. ZIP 위치 순서로 이어서 계산한다                                             | scramble 전 평문의 ZIP 전체. ZIP 위치 순서로 이어서 계산한다      |
| 본문 손상 | manifest는 헤더 CRC가 잡는다. 텍스트는 ZIP 항목 CRC32가 잡는다. asset은 열 때 검사하지 않는다             | 모든 본문을 헤더 CRC가 잡는다. 텍스트는 ZIP 항목 CRC32도 비교한다 |

버전 1의 범위 규칙:

- 로컬 헤더 범위는 30바이트 + 이름 길이다.
- 로컬 헤더의 extra 길이는 0이다. 디코딩은 0이 아니면 `zip-corrupt`로 거부한다. 인코딩은 extra를 쓰지 않는다("ZIP 쓰기").
- 이 코덱이 만든 ZIP만 받는다. 그래서 로컬 헤더 범위를 중앙 디렉터리의 이름 길이만으로 정할 수 있다.
- manifest 본문 범위는 manifest 로컬 헤더 바로 뒤에서 시작해 중앙 디렉터리가 적은 압축 크기만큼이다.
- CRC는 로컬 헤더들, manifest 본문, 중앙 디렉터리 + 끝 레코드를 ZIP 위치 순서로 이어서 계산한다. 인코딩과 디코딩의 순서가 같아야 한다.
- 범위마다 `scramble(조각, 시작 위치)`로 섞는다. 위치는 ZIP 안 위치다.
- 봉인은 섞는 조각만 새 버퍼로 만든다(`src/seal.ts`). 나머지 조각은 asset `Blob`을 포함해 그대로 출력에 담는다.
- 열기는 읽은 범위마다 새 배열에 푼다(`src/metadata-scramble.ts`). 입력을 고치지 않는다.
- manifest를 뺀 본문은 섞지 않았으므로 복원하지 않는다. asset 본문은 읽지도 않는다("읽기 방식").
- 헤더 CRC는 로컬 헤더와 중앙 디렉터리가 적은 항목 CRC32를 통해 저장 시점의 본문을 간접으로 반영한다. 저장한 뒤 본문이 고쳐진 것은 헤더 CRC가 잡지 못한다.
- 로컬 헤더의 이름 길이는 중앙 디렉터리와 같아야 한다. 이 코덱이 만든 ZIP이라서 다르면 거부한다.

버전 2의 범위 규칙:

- 위치 0부터 ZIP 끝까지 모든 바이트를 `scramble(조각, 시작 위치)`로 섞는다. 위치는 ZIP 안 위치다.
- CRC는 섞기 전 ZIP을 처음부터 끝까지 이어서 계산한다.
- 봉인은 모든 조각을 새 버퍼로 섞는다(`src/full-scramble.ts`). 입력을 고치지 않는다.
  - asset `Blob`은 `CHUNK_BYTES`씩 읽어 섞고, 섞은 조각을 곧바로 `Blob` 조각으로 만든다.
  - 인코딩은 asset을 두 번 읽는다. 항목 CRC32를 계산할 때 한 번, 섞을 때 한 번이다.
- 열기는 읽은 범위를 읽는 즉시 ZIP 위치를 기준으로 평문으로 되돌리는 읽기 수단을 쓴다(`createUnscrambledReader`). 이후 단계는 두 버전이 같은 코드를 지난다.
- 로컬 헤더의 extra 길이는 0이고, 로컬 헤더의 이름 길이는 중앙 디렉터리와 같아야 한다. 버전 1과 같다.
- asset 본문도 섞여 있으므로 입력의 `slice`가 원본 바이트가 아니다. 디코딩은 본문을 `CHUNK_BYTES`씩 읽어 평문으로 되돌린 새 `Blob`을 만든다.

### scramble 키

- 키는 16바이트 `Uint8Array`다. 길이가 다르면 던진다.
- 키를 LE uint32 4개로 읽는다. 0~2번 워드는 키스트림에 쓰고 3번 워드는 치환표 시드에 쓴다.
- 치환표는 봉인·열기 한 번에 한 번 만든다. 키마다 캐시하지 않는다.
- 기본 키 `DEFAULT_SCRAMBLE_KEY`가 있다. 인코딩 옵션 `scrambleKey`와 디코딩 옵션 `scrambleKeys`를 비우면 쓴다. 키 값은 문서에 적지 않는다.
- 호출자가 내보낸 `DEFAULT_SCRAMBLE_KEY` 배열을 바꿔도 기본 동작은 변하지 않는다. 코덱이 내부 사본을 쓴다.
- 키 확인값은 키 16바이트의 CRC32다. 헤더가 적는다.
- 키 확인값은 공개되어도 된다. scramble은 기밀성을 약속하지 않는다.
- 인코딩은 `scrambleKey` 하나로 봉인한다.
- 디코딩은 `scrambleKeys`에서 키 확인값이 헤더와 같은 키를 고른다. 없으면 `scramble-key-mismatch`다.
- 확인값은 키를 고르는 데만 쓴다. 고른 키가 맞는지는 복원과 CRC가 본다("검사 순서"의 7단계).
- `scrambleKeys` 규칙:
  - 목록을 주면 목록의 키만 쓴다. 기본 키를 자동으로 더하지 않는다. 기본 키도 받으려면 호출자가 목록에 넣는다.
  - 빈 배열은 던진다.
  - 키 확인값이 같은 키가 둘 이상이면 던진다. 어느 키로 풀지 정할 수 없기 때문이다.

#### scramble 알고리즘

- 다른 언어 구현이 같은 바이트를 내도록 절차를 공개한다.
- scramble은 처음부터 기밀성과 변조 방지를 약속하지 않는다("scramble"). 절차를 공개해도 잃는 보장이 없다.
- 구현은 이 절의 절차와 `test-vectors/vectors.json`의 `defaultScrambleTable`, `defaultScrambleStream`이 같은 결과를 내는지 맞춰 본다.

연산 약속:

- 모든 값은 부호 없는 32비트 정수(u32)다. 결과가 2^32를 넘으면 하위 32비트만 남긴다.
- 예외는 치환표의 `j` 계산이다. 곱 `u * (i + 1)`은 하위 32비트로 자르지 않고 64비트 정수로 계산한다.
- `a ^ b`, `a | b`, `a & b`는 비트 XOR, OR, AND다.
- `a >> n`은 부호 없는 오른쪽 시프트다. 빈 자리는 0이다. 부호 비트를 채우는 산술 시프트가 아니다.
- `a + b`는 더한 뒤 하위 32비트만 남긴다.
- `mul32(a, b)`는 a와 b의 곱에서 하위 32비트만 남긴다. 곱은 64비트 이상으로 계산한다. JavaScript의 `Math.imul`과 같은 비트 패턴이다.
- 부호 있는 32비트 정수로 계산하는 언어는 `>>`를 부호 없는 시프트로 하고, 아래 `u * (i + 1)`을 계산하기 전에 u를 부호 없는 값으로 바꾼다.
- 워드 `wk`(k = 0..3)는 키 바이트 `키[4k + m]`(m = 0..3)로 `키[4k] + 키[4k + 1] * 2^8 + 키[4k + 2] * 2^16 + 키[4k + 3] * 2^24`다. 앞 바이트가 낮은 자리다.

치환표 만들기. 입력은 시드 `w3`이다. 출력은 길이 256의 `표`다.

```text
표[x] = x                                  (x = 0..255)
상태 = w3
i = 255 부터 1 까지 1씩 줄이며 반복:
    상태 = 상태 + 0x6D2B79F5
    r = mul32(상태 ^ (상태 >> 15), 상태 | 1)
    r = r ^ (r + mul32(r ^ (r >> 7), r | 61))
    u = r ^ (r >> 14)
    j = (u * (i + 1)) >> 32                (64비트 정수 곱, 상위 32비트)
    표[i] 와 표[j] 의 값을 맞바꾼다
```

- `i`마다 난수 한 개(`u`)를 쓴다. 반복은 255번이다.
- `j`는 0 이상 `i` 이하다.
- 곱 `u * (i + 1)`은 2^40 미만이다.
- 배정밀도 소수로 계산하는 구현은 `floor(u / 2^32 * (i + 1))`로 같은 `j`를 얻는다. 이 곱과 2^32 나눗셈은 배정밀도에서 정확하다.
- 역표는 `역표[표[x]] = x`다.

위치별 키스트림 바이트. 입력은 `w0`, `w1`, `w2`와 위치 `p`다. 출력은 0~255 한 바이트다.

```text
x = p ^ w0
x = mul32(x ^ (x >> 16), 0x85EBCA6B)
x = mul32(x ^ (x >> 13) ^ w1, 0xC2B2AE35)
x = x ^ (x >> 16)
x = mul32(x ^ w2, 0x27D4EB2F)
키스트림(p) = (x ^ (x >> 15)) & 0xFF
```

- `p`는 ZIP 안 위치다. 첫 바이트가 0이다.
- 나눠 섞는 조각에서 인덱스 `n`(조각의 첫 바이트가 0)인 바이트의 위치는 `시작 위치 + n`이다.
- 계산은 `p`의 하위 32비트만 쓴다. 유효한 파일은 ZIP 길이가 2^32 미만이라 `p`가 2^32에 닿지 않는다.
- 섞기는 `표[바이트 ^ 키스트림(p)]`, 되돌리기는 `역표[바이트] ^ 키스트림(p)`다.

## 검사 순서

디코딩은 아래 순서로 검사하고 처음 걸린 이유를 돌려준다. 2~5단계는 헤더만 보며 키가 필요 없다.

1. 입력 크기와 읽기. "입력 크기 상한"을 넘으면 읽지 않고 `input-too-large`(`maxBytes`에 상한). 풀린 크기 합계 초과는 10단계의 `limit-exceeded`(`maxUncompressedBytes`)다. 헤더 범위를 읽지 못하면 `read-failed`. 이후 단계의 읽기가 실패해도 `read-failed`다("읽기 방식").
2. magic. 4바이트가 안 되거나 `OCOD`가 아니면 `bad-magic`.
3. 헤더 길이와 포맷 버전. 22바이트 미만이면 `length-mismatch`. 1과 2가 아닌 버전은 `unsupported-version`.
4. kind.
   - kind 길이 N이 0이거나 64를 넘으면 `kind-invalid`.
   - 22 + N바이트 미만이면 `length-mismatch`.
   - kind 문자열이 규칙을 어기면 `kind-invalid`. 규칙을 지켰지만 기대한 kind와 다르면 `kind-mismatch`.
5. 전체 크기. 22 + N + payload 길이와 다르면 `length-mismatch`. 잘림과 덧붙음을 모두 잡는다.
6. 키. 헤더의 키 확인값과 같은 키가 없으면 `scramble-key-mismatch`.
7. 복원과 CRC32. 메타데이터와 manifest 본문을 되돌린다. 끝 레코드의 항목 수가 `maxFiles` + `maxFolders` + 2를 넘으면 로컬 헤더를 읽기 전에 `zip-corrupt`. 범위를 정할 수 없으면 `zip-corrupt`, CRC가 헤더와 다르면 `crc-mismatch`. CRC 범위는 버전 1이 섞는 범위, 버전 2가 ZIP 전체다. 버전 2에서 ZIP 전체를 읽지 못하면 `read-failed`.
8. ZIP 항목 목록. 암호화 항목, 읽지 못하는 이름, 겹치는 이름, 틀린 로컬 헤더 시그니처, `centralStart`를 넘는 압축 데이터는 `zip-corrupt`. 중앙 디렉터리의 구조 손상은 7단계가 먼저 거부한다. 내용은 풀지 않는다.
9. manifest. 선언 크기가 1 MiB(`MANIFEST_MAX_BYTES`)를 넘거나 형식이 틀리면 `manifest-invalid`. `manifest.json` 항목이 없으면 7단계에서 `zip-corrupt`다. 풀리지 않으면 `zip-corrupt`. 헤더와 kind가 다르면 `manifest-kind-mismatch`.
10. 항목 대응, 이름, 한도.
    - ZIP 항목이 manifest와 맞지 않으면 `manifest-invalid`.
    - 이어서 ZIP 중앙 디렉터리가 선언한 크기로 이름과 한도를 검사한다. `invalid-name`, `limit-exceeded`.
11. 파일 내용. manifest 순서로 항목마다 본다.
    - 텍스트는 풀린 길이가 선언과 다르거나 UTF-8이 아니면 `zip-corrupt`.
    - deflate(방식 8) 텍스트는 압축 크기가 0이면 `zip-corrupt`. 유효한 deflate 스트림은 비어 있을 수 없다. 인코더는 빈 텍스트도 압축 크기 2로 쓴다. 저장(방식 0) 텍스트는 크기 0이어도 받는다.
    - asset은 저장(방식 0)이 아니거나 압축 크기가 선언 크기와 다르면 `zip-corrupt`.

7단계:

- `centralStart`부터 끝까지 푼다. 끝 레코드가 ZIP의 마지막 22바이트이고 `centralStart`가 헤더와 같아야 한다.
- 로컬 헤더를 읽기 전에 끝 레코드의 항목 수를 호출자 `limits`의 `maxFiles` + `maxFolders` + 2와 비교한다. 넘으면 읽지 않고 거부한다. 인코더는 한도 안에서 이 수를 넘는 파일을 만들지 않으므로 "인코딩은 디코딩이 거부할 파일을 만들지 않는다"는 계약은 유지된다.
- 중앙 디렉터리의 항목마다 로컬 헤더(30바이트 + 이름)를 푼다. 이름 길이와 extra 길이를 검사한다.
- `manifest.json` 항목은 로컬 헤더를 푼 뒤 본문도 푼다. 본문은 헤더 바로 뒤에서 시작해 중앙 디렉터리의 압축 크기만큼이다.
- 아래는 `zip-corrupt`다.
  - `centralStart`가 ZIP 밖이거나 끝 레코드와 다르다.
  - 끝 레코드의 항목 수가 `maxFiles` + `maxFolders` + 2를 넘는다. 합 이하에서 `maxFiles`나 `maxFolders` 한 항목만 넘으면 10단계의 `limit-exceeded`다.
  - 중앙 디렉터리가 끝 레코드와 맞지 않는다.
  - 중앙 디렉터리 항목이 범위를 벗어나거나 시그니처가 틀리다.
  - `manifest.json` 항목이 없거나 둘이다.
  - 로컬 헤더나 manifest 본문이 겹치거나 `centralStart`를 넘는다. manifest 본문이 ZIP 밖까지 가는 경우를 포함한다.
  - 로컬 헤더의 이름 길이가 중앙 디렉터리와 다르다.
  - 로컬 헤더의 extra 길이가 0이 아니다.
- 범위를 정할 수 있는 손상은 CRC가 `crc-mismatch`로 잡는다. 범위 안 어느 한 바이트를 고쳐도 `crc-mismatch`나 `zip-corrupt`다. 버전 2의 범위는 ZIP 전체다.
- 버전 2는 위 구조 검사를 마친 뒤 ZIP 전체를 `CHUNK_BYTES`씩 순서대로 읽어 평문 CRC를 이어서 계산한다.
  - 구조 손상은 CRC가 틀려도 `zip-corrupt`다. 버전 1과 같은 순서다.
  - 입력 크기 상한이 읽는 양을 묶는다.
  - 이 읽기를 11단계의 읽기와 합치지 않는다. 파일 내용이 텍스트인지 asset인지는 9단계에서 manifest를 풀어야 안다. CRC는 그보다 앞 단계다.
- 복원은 읽은 조각마다 새 배열에 푼다. 입력을 고치지 않고 전체를 복사하지도 않는다. 호출자가 넘긴 `Uint8Array`도 같다.
- 복원한 중앙 디렉터리는 이 단계에서 ZIP 읽기 코드(`readCentralRecords`)가 한 번 읽는다. 끝 레코드와 항목의 구조를 여기서 검사한다.
- 8단계부터는 그 레코드와 복원한 로컬 헤더를 ZIP 읽기 코드(`readZipEntries`, `inflateEntry`)가 읽는다.

8단계의 ZIP 읽기(`zip.ts`):

- CRC 비교 뒤에 본다. 같은 입력의 CRC가 헤더와 다르면 7단계의 `crc-mismatch`가 먼저다.
- 끝 레코드, 중앙 디렉터리 항목의 범위와 시그니처, 로컬 헤더 위치는 7단계가 CRC 비교 전에 검사한다. 이 손상은 CRC가 틀려도 `zip-corrupt`다.
- 아래는 `zip-corrupt`다.
  - 암호화 항목.
  - 읽지 못하는 이름. UTF-8 표시가 없으면 ASCII 이름만 받는다.
  - 이름이 겹치는 항목.
  - 로컬 헤더 시그니처가 틀린 항목.
  - 압축 데이터가 `centralStart`를 넘는 항목.
- 저장(0)과 deflate(8) 밖의 압축 방식은 내용을 풀 때(manifest는 9단계, 파일은 11단계) `zip-corrupt`다.
- 이 코덱이 만드는 모양의 ZIP만 받는다.

11단계의 텍스트 항목:

- 텍스트 항목은 푼 뒤 중앙 디렉터리의 CRC32와 비교한다. 다르면 `zip-corrupt`. 길이가 같은 손상도 잡는다.
- 텍스트 본문은 헤더 CRC 범위 밖이다. 이 비교가 본문 손상을 보는 유일한 검사다.
- manifest는 이 비교를 하지 않는다. 헤더 CRC 범위에 manifest 압축 바이트와 중앙 디렉터리의 항목 CRC32가 함께 든다.

11단계의 asset 항목:

- 저장(방식 0)이어야 하고 압축 크기가 선언 크기와 같아야 한다. 아니면 `zip-corrupt`다.
- 이유: 버전 1은 디코딩 출력의 `Blob`이 입력의 본문 범위 그대로다. 범위가 곧 원본 바이트여야 한다.
- 버전 1은 본문을 읽거나 풀지 않는다.
- 버전 2는 본문을 `CHUNK_BYTES`씩 읽어 평문으로 되돌린 새 `Blob`을 만든다. 읽지 못하면 `read-failed`다.
- 디코딩은 asset의 항목 CRC32를 확인하지 않는다. 인코딩은 이 값을 계산해 ZIP 항목에 적는다.
- 열 때 asset 손상은 버전 1이 잡지 못한다. 버전 2는 7단계의 헤더 CRC가 잡는다.

공통:

- 파일 내용은 10단계를 통과한 뒤에만 푼다. 선언 크기 합계가 메모리와 해제 CPU의 상한이다.
- 10단계는 항목마다 파일 수와 폴더 수를 본다. ZIP 폴더 항목이 수만 개여도 검사 비용이 한도에 묶인다.
- 형제 중복은 부모 번호와 조각으로 찾는다. 항목마다 접두 경로 문자열을 만들면 깊은 경로에서 비용이 경로 길이의 제곱이 된다.
- 항목은 선언 크기 버퍼에 푼다. deflate는 출력이 선언 크기를 넘는 순간 멈춘다.
- ZIP 목록은 코덱이 직접 읽는다. fflate `unzipSync`는 선언 크기 버퍼에 풀지만 넘치는 deflate 스트림도 끝까지 해제한다. 메모리는 막고 CPU는 막지 못한다.
- 해제는 fflate `Inflate`에 압축 데이터를 16 KiB씩 민다. 한 번에 풀리는 출력은 그 약 1,032배 이하다.
- 항목 이름의 맨 앞 U+FEFF는 떼지 않는다. 떼면 다른 항목과 같은 이름이 된다.
- 변조 방지가 아니다. CRC와 scramble 규칙이 모두 클라이언트에 있다.
- 인코딩도 10단계의 이름과 한도 검사를 한다. 결과가 입력 크기 상한을 넘으면 만들지 않는다. 디코딩이 거부할 파일은 만들지 않는다.
- 인코딩은 10단계 검사 뒤, 결과를 입력 크기 상한과 비교하기 전에 manifest 바이트 길이를 잰다. 1 MiB(`MANIFEST_MAX_BYTES`)를 넘으면 만들지 않고 `manifest-too-large`를 돌려준다. 디코딩은 이 이유를 돌려주지 않는다. 9단계에서 `manifest-invalid`다.
- 인코딩은 manifest 길이 검사 뒤 ZIP을 쓰면서 asset `Blob`을 읽는다. 읽기는 결과를 입력 크기 상한과 비교하기 전에 일어난다.
  - 읽지 못하면 만들지 않고 `read-failed`와 읽지 못한 asset의 `path`를 돌려준다. `path`는 `files/`를 뗀 경로다.
  - 읽지 못한 asset이 여럿이면 ZIP에 쓰는 순서("항목 순서")로 처음 읽지 못한 하나만 알린다.
  - 앞의 이름·한도·manifest 길이 검사에서 걸리면 asset을 읽지 않는다.
  - 호출자 버그로 던지는 오류는 이 이유로 바꾸지 않는다.
- 버전 2의 인코딩은 입력 크기 상한 비교 뒤 asset을 섞으려고 한 번 더 읽는다. 이 읽기의 실패도 `read-failed`와 `path`로 돌려준다.
- 경로가 길수록 manifest가 크다. 경로가 모두 1,024 코드 유닛의 비 ASCII이면 파일 약 340개에서 넘는다. `maxFiles`가 이보다 크면 한도 안의 입력도 `manifest-too-large`가 될 수 있다.
- 10단계는 폴더를 먼저, 파일을 나중에 검사한다. 디코딩은 ZIP 폴더 항목 다음 manifest 파일 순서다. 인코딩은 `folders` 다음 `entries` 순서다.
- 위반이 여럿이면 처음 걸린 하나만 돌려준다. 그래서 어느 경로를 알리는지는 이 순서를 따른다. 예: 폴더 `x` 안의 잘못된 파일과 형제 폴더 `y`의 잘못된 이름이 함께 있으면 `y`를 알린다.

## 한도

`ProjectFileLimits`의 항목 뜻은 `packages/projectfile/README.md`의 limits 절에 있다. 여기서는 세는 규칙과 검사 순서를 정한다.

- 인코딩과 디코딩이 같은 한도로 검사한다. 만든 파일을 같은 한도로 못 여는 일이 없다.
- 코드와 asset은 `rules.isCode`로 나눈다. 텍스트 항목만 코드가 될 수 있다. asset 노드는 늘 asset 한도에 센다.
- `maxUncompressedBytes`는 파일 내용의 합이다. `manifest.json`과 폴더 항목은 세지 않는다.
- `maxFolders`는 서로 다른 폴더 경로의 수다. 폴더 항목 없이 파일 경로의 조상으로만 나오는 폴더도 센다.
- `maxFolders`는 입력 크기 상한의 항목 수를 묶으려고 둔다.
- `maxUncompressedBytes`는 `MAX_UNCOMPRESSED_BYTES_CEILING` 이하여야 한다. 값은 256 MiB(268,435,456바이트)다. 넘는 한도는 호출자 버그라서 인코딩과 디코딩이 던진다.
  - 이유: 입력 크기 상한(`maxProjectFileBytes`)과 해제 메모리가 이 값으로 묶인다.
  - 올려도 포맷은 바뀌지 않는다. 올린 버전이 만든 큰 파일을 옛 버전은 `input-too-large`나 `limit-exceeded`로 거부할 수 있다.
  - 상한을 올리면 "입력 크기 상한"의 uint32 검토를 다시 한다.
- `maxFiles` + `maxFolders` + 2는 65,535(`MAX_ZIP_ENTRIES`) 이하여야 한다. ZIP 끝 레코드의 항목 수가 uint16이고 ZIP64를 쓰지 않기 때문이다. 2는 `manifest.json`과 `files/` 폴더 항목이다. 넘는 한도는 호출자 버그라서 인코딩과 디코딩이 던진다.

검사 순서(`check.ts`):

1. 항목마다 이름 규칙과 형제 중복을 본다. 이어서 파일 개수(`maxFiles`)와 폴더 개수(`maxFolders`)를 본다.
2. asset 하나(`maxAssetBytes`).
3. asset 합계(`maxAssetsTotalBytes`).
4. 코드 합계(`maxCodeBytes`).
5. 전체 합계(`maxUncompressedBytes`).

### 입력 크기 상한

디코딩은 읽기 전에 입력 크기를 `maxProjectFileBytes(limits)`와 비교한다. 넘으면 `input-too-large`이고 `maxBytes`에 이 상한을 담는다. 한도 안의 항목을 인코딩한 파일이 넘을 수 없는 크기다. 이 함수도 잘못된 한도에 던진다.

| 부분                 | 크기                                                               |
| -------------------- | ------------------------------------------------------------------ |
| 헤더와 ZIP 끝 레코드 | 86 + 22바이트. 헤더는 최대 길이(`MAX_HEADER_BYTES`)로 잡는다       |
| 데이터               | `maxUncompressedBytes` + manifest 상한 1 MiB                       |
| deflate 여유         | 데이터 7,000바이트마다 5바이트                                     |
| 항목마다             | 지역 헤더 30 + 중앙 디렉터리 46 + deflate 여유 10 + 이름 두 번     |
| 항목 수              | `maxFiles` + `maxFolders` + 2(`manifest.json`, `files/` 폴더 항목) |

- 이름은 `files/`, 경로, 폴더 끝 `/`다. 경로는 최대 1,024(`MAX_PATH_LENGTH_CEILING`) UTF-16 코드 유닛이고 유닛마다 UTF-8 3바이트 이하다. 그래서 이름은 3,079바이트 이하다.
- 항목마다 오버헤드는 30 + 46 + 10 + 2 × 3,079 = 6,244바이트다.
- 데이터가 `data`일 때 상한은 `86 + 22 + data + ceil(5 × data / 7000) + 항목 수 × 6,244`다.
- `rules.maxPathLength`는 1,024 이하여야 한다. 넘으면 인코딩과 디코딩이 던진다.
- 1,024를 올리면 입력 크기 상한이 커져 옛 버전이 새 파일을 거부한다. 올리지 않는다.
- deflate 여유는 fflate가 항목마다 잡는 출력 버퍼 `n + 5 * (1 + ceil(n / 7000))`에서 나온다. asset과 폴더 항목은 저장이라 이 여유를 쓰지 않는다. 그만큼 상한이 넉넉하다.
- 인코딩은 폴더 수와 파일 수를 검사하므로 결과가 이 상한을 넘지 않는다.
- 상한은 uint32 안이다. `maxUncompressedBytes`가 절대 상한이고 항목 수가 최대(65,535)일 때 678,877,169바이트다.
  - 이유: 헤더의 payload 길이와 `centralStart`가 uint32다. 상한이 uint32를 넘으면 한도 안의 파일이 이 필드를 넘칠 수 있다.
- 이 값은 `readProjectFileHeader`가 보지 않는다("readProjectFileHeader").

## 이름 규칙

각 항목의 경로를 `/`로 나눠 조각마다 검사한다.

- 경로 전체 길이가 `rules.maxPathLength`를 넘으면 `path-too-long`이다. 조각 검사보다 먼저 본다.
- 조각마다 호출자 규칙(`checkSegment`)이 먼저, 라이브러리의 무결성 규칙이 다음이다. 호출자 규칙은 무결성 규칙을 풀 수 없다.
- 마지막 조각은 항목 종류(`text`=`file`, `asset`, 폴더)를 따르고 나머지는 `folder`다.
- 조각 검사를 모두 통과한 항목에 형제 중복 검사를 한다.

호출자 규칙의 몫: 조각 길이(`too-long`), 허용하지 않는 확장자(`invalid-extension`, `invalid-asset-extension`), 폴더 이름의 `.`(`folder-dot`). 라이브러리는 이 값을 판정하지 않는다.

라이브러리가 항상 강제하는 무결성 규칙:

- 빈 조각(앞 `/`, `//`, 공백만 있는 조각)은 `empty`다.
- `.`·`..` 조각, `\`, 제어 문자는 `invalid-char`다.
- 짝 없는 서로게이트(U+D800..U+DFFF 코드 유닛)가 있는 조각은 `invalid-char`다. ZIP 항목 이름의 UTF-8 인코딩은 이 유닛을 U+FFFD로 바꿔 manifest 경로와 달라진다. 올바른 쌍(예: 이모지)은 받는다.
- 앞뒤 공백이 있는 조각은 `invalid-char`다. 공백을 떼면 ZIP 항목에서는 다른 이름이 된다.
- 공백은 ECMAScript `String.prototype.trim`이 떼는 문자(WhiteSpace, LineTerminator)다. U+FEFF와 U+00A0도 공백이다.
- 형제 사이 이름 중복은 `duplicate`로 거부한다. 폴더와 파일 사이도 같다.
  - 중복 판정 키는 조각을 소문자로 바꾼 뒤 NFC로 정규화한 값이다. 키가 같으면 중복이다.
  - 대소문자만 다른 이름과 정규형만 다른 이름이 같은 키가 된다. 예: U+00E9와 U+0065 U+0301, 한글 음절 U+AC00과 자모 조합 U+1100 U+1161.
  - 소문자 변환을 먼저 한다. 소문자 결과가 NFC가 아닐 수 있어서 순서를 바꾸면 키가 달라진다. 예: U+03A9 U+0342와 U+03C9 U+0342는 이 순서에서만 같은 키다.
  - 합치는 것은 정규 동치(NFC)뿐이다. 호환 동치(NFKC)는 합치지 않는다. 예: 합자 U+FB01과 `fi`는 다른 이름이다.
  - 소문자 변환은 ECMAScript `String.prototype.toLowerCase`다. 유니코드 기본 대소문자 변환(toLowercase)이며 로캘 규칙을 쓰지 않는다. 예: U+0130은 U+0069 U+0307이 되어 `i`와 다른 이름이다.
  - 대소문자 접기(case folding)가 아니다. 예: `ß`와 `SS`는 다른 이름이다.
  - 시그마의 단어 끝 규칙(Final_Sigma)은 조각 전체를 문맥으로 본다. 예: U+0391 U+03A3의 키는 U+03B1 U+03C2다. 뒤에 `.txt`가 붙으면 U+03B1 U+03C3 `.txt`다. `.`은 Case_Ignorable이라 문맥 판정에서 건너뛴다.
  - 정규화와 소문자 변환은 실행 환경의 유니코드 데이터를 따른다. 유니코드 버전이 다르면 그 사이에 추가된 문자에서 키가 갈려, 같은 파일을 한쪽은 받고 다른 쪽은 거부할 수 있다. 예: 유니코드 15 뒤에 추가된 U+A7CB의 소문자는 U+0264다. 유니코드 15 데이터에는 이 매핑이 없어 두 이름이 다른 키가 된다.
  - 키는 판정에만 쓴다. 저장하고 복원하는 이름은 입력 그대로다.
  - 경로 길이 상한과 조각 규칙은 정규화 전 이름으로 검사한다.
  - 키 길이는 조각 길이의 3배 이하다. NFC가 코드 유닛 하나를 셋까지 늘릴 수 있다(예: U+FB2C). 소문자 변환에서 길이가 느는 문자는 U+0130 하나이고, 그 결과는 NFC에서 늘지 않는다.
- 같은 폴더를 폴더 항목과 파일의 조상으로 두 번 세는 것은 중복이 아니다. 대소문자와 정규형까지 포함해 글자가 그대로 같아야 한다.

거부 이유(`cause`)의 집합은 `ProjectNameCause`다. 라이브러리가 직접 판정하는 값은 `empty`, `invalid-char`, `duplicate`, `path-too-long`이다.

## 알려진 한계

- 버전 1은 열 때 asset 본문 손상을 검사하지 않는다. 헤더 CRC가 메타데이터 범위와 manifest 본문만 본다. asset은 ZIP 항목 CRC32도 비교하지 않는다. 버전 2는 헤더 CRC가 ZIP 전체를 본다.
- 버전 1은 섞지 않는 본문에 평문이 남는 경우가 있다. 비 ASCII 텍스트의 stored 블록과 asset 원본이다. manifest 본문은 섞으므로 파일 경로는 남지 않는다("ZIP과 manifest"). 버전 2는 남지 않는다.
- 텍스트와 manifest는 전부 메모리에 올린다. asset 본문은 `Uint8Array`로 올리지 않는다.
  - 인코딩: 텍스트와 deflate 결과, 섞은 조각이 메모리에 있다. asset `Blob`은 CRC32를 계산하려고 1 MiB(`CRC_CHUNK_BYTES`)씩 읽는다. 버전 2는 섞으려고 `CHUNK_BYTES`씩 한 번 더 읽는다.
  - 디코딩: `Blob` 입력은 필요한 범위만 읽는다("읽기 방식"). `Uint8Array` 입력은 asset마다 그 범위를 복사한 `Blob`을 만든다.
  - 버전 2의 디코딩은 payload 전체를 읽고, asset마다 평문으로 되돌린 새 `Blob`을 만든다. 같은 입력을 버전 1로 인코딩한 파일보다 시간이 든다. 측정은 `docs/adr/0007-full-scramble-version.md`에 있다.
- 항목 수 한도는 10단계에서 본다. 그 전에 중앙 디렉터리 항목마다 범위와 조각을 만든다. 손상 파일은 항목이 많을수록 한도 검사 전 메모리가 커진다.
  - 끝 레코드 항목 수가 `maxFiles` + `maxFolders` + 2를 넘으면 7단계가 로컬 헤더를 읽기 전에 거부한다. 그래서 이 메모리는 호출자 한도의 합에 묶이고, 합의 최대는 65,535다.
  - 측정은 항목 65,000개인 6.4 MB 파일이다. Node에서 heap 증가는 `Blob` 입력 약 162 MB, `Uint8Array` 입력 약 71 MB였다. 이 값은 합이 65,000 이상인 한도에서만 나온다. 합이 작은 한도의 메모리는 재지 않았다.

## 읽기 방식

이 절은 포맷 버전 1의 읽기 방식이다. 버전 2는 "버전 2의 읽기"가 다르게 정한다.

디코딩은 `Blob` 입력에서 필요한 범위만 읽는다. 입력 전체를 읽지 않는다.

읽는 범위:

- 헤더: 입력의 앞 86바이트(`MAX_HEADER_BYTES`)와 입력 크기 중 작은 쪽.
- 중앙 디렉터리와 끝 레코드: `centralStart`부터 끝까지.
- 로컬 헤더: 중앙 디렉터리가 가리키는 항목마다 30바이트 + 이름.
- 압축 본문: `manifest.json`과 방식이 0이 아닌(deflate) 항목.
- 저장(방식 0)한 텍스트 본문: manifest로 텍스트임을 확인한 뒤 읽는다.

읽지 않는 범위:

- 저장(방식 0)한 asset 본문. 디코딩 출력의 `Blob`이 입력의 이 범위를 가리킨다.
- 이유: 디코딩이 asset 본문을 쓰지 않는다. 읽으면 시간과 메모리만 든다.

읽기 호출 수:

- 읽기 호출은 항목 수 + 다시 읽는 텍스트 수 + 2 이하다. 항목 수는 ZIP 항목 수다(`manifest.json`, `files/`, 폴더, 파일).
- 다시 읽는 텍스트는 7단계에서 본문을 읽지 않은 텍스트다. 저장(방식 0)한 텍스트와 압축 크기를 0으로 선언한 deflate 텍스트다. 10단계 뒤에 하나씩 읽는다. 뒤의 것은 읽은 뒤 11단계가 `zip-corrupt`로 거부한다.
- 인코더는 두 텍스트를 만들지 않는다. 빈 텍스트도 deflate 본문이 비어 있지 않다. 인코더가 만든 파일은 항목 수 + 2 이하다.
- 손상 파일도 상한이 있다. 항목 수는 7단계에서 `maxFiles` + `maxFolders` + 2 이하로 막는다. 다시 읽는 텍스트는 10단계에서 파일 수가 `maxFiles` 이하인지 본 뒤에 읽는다. 그래서 읽기 호출은 2 × `maxFiles` + `maxFolders` + 4 이하다.
- 방식이 0이 아닌 asset 항목은 11단계에서 거부하는 파일이다. 이 항목의 본문은 읽을 수 있다.
- 동시에 진행하는 읽기는 16개 이하다. 손상 파일은 읽기 호출이 항목 수(최대 `maxFiles` + `maxFolders` + 2, 65,535 이하)만큼 나올 수 있고, 한꺼번에 읽으면 한도 검사 전에 메모리가 커진다.

읽기 실패:

- 어느 읽기가 실패해도 `read-failed`다. 읽은 바이트가 요청한 범위보다 짧아도 `read-failed`다.
- 저장한 텍스트 본문은 10단계 뒤, 11단계의 항목 검사 앞에서 읽는다. 이 읽기의 실패는 11단계의 `zip-corrupt`(텍스트 내용, asset 방식)보다 먼저 보고된다.

`Uint8Array` 입력:

- 읽지 않고 부분 뷰를 쓴다. 입력을 바꾸지 않고 전체를 복사하지 않는다.
- asset은 그 범위를 복사한 `Blob`이다.

### 버전 2의 읽기

버전 2는 헤더 CRC가 ZIP 전체를 보고 asset 본문이 섞여 있어서 입력 전체를 읽는다.

- 버전 1과 같은 범위(헤더, 중앙 디렉터리, 로컬 헤더, 압축 본문, 저장 텍스트 본문)를 읽는다. 읽자마자 ZIP 위치를 기준으로 평문으로 되돌린다.
- 7단계에서 ZIP 전체를 `CHUNK_BYTES`씩 순서대로 읽어 CRC를 계산한다.
- 11단계에서 asset 본문을 `CHUNK_BYTES`씩 순서대로 읽어 평문 `Blob`을 만든다.
- 읽기 호출은 버전 1의 상한에 두 값을 더한 수 이하다.
  - payload 길이를 `CHUNK_BYTES`로 나눈 올림.
  - asset마다 선언 크기를 `CHUNK_BYTES`로 나눈 올림의 합.
- 두 읽기는 순차라서 동시에 진행하는 읽기 수의 상한(16개)은 그대로다.
- 어느 읽기가 실패해도 `read-failed`다. 읽은 바이트가 범위보다 짧아도 같다.
- `Uint8Array` 입력은 읽지 않고 부분 뷰에서 새 배열로 되돌린다. 입력을 바꾸지 않는다.
- 입력 전체를 읽으므로 시간은 입력 크기에 비례한다. 입력 크기는 `maxProjectFileBytes(limits)`가 묶는다.

## readProjectFileHeader

키 없이 헤더만 읽고 검사하는 함수다. 서버가 업로드된 파일의 헤더만 검사하는 용도다. 서버는 키가 없고 내용을 열 필요가 없다.

- 읽는 범위: 입력의 앞 86바이트(`MAX_HEADER_BYTES`)와 입력 크기 중 작은 쪽. `Blob` 입력도 이 범위만 읽는다.
- 검사: 디코딩의 1단계 중 헤더 읽기와 2~5단계("검사 순서").
- 실패 이유는 디코딩의 해당 단계와 같다: `read-failed`, `bad-magic`, `length-mismatch`, `unsupported-version`, `kind-invalid`. 두 함수가 같은 헤더 읽기 코드를 쓴다.
- 입력 크기 상한은 보지 않는다. `limits`를 받지 않으므로 1단계의 크기 검사를 하지 않는다. 입력 크기를 제한하려면 호출자가 `maxProjectFileBytes` 같은 값으로 직접 검사한다.
- 기대한 kind를 받지 않는다. 그래서 `kind-mismatch`는 나오지 않고 kind 길이나 문자열이 규칙을 어기면 `kind-invalid`다. kind 비교는 호출자가 돌려받은 `kind`로 한다.
- 키 확인값 일치(6단계), CRC(7단계), ZIP과 manifest(8단계 이후)는 보지 않는다. 통과해도 파일이 열린다는 뜻이 아니다.
- 열 수 없는 입력은 던지지 않고 `ProjectFileFailure`를 돌려준다.

돌려주는 값(`ProjectFileHeaderInfo`)은 헤더의 포맷 버전(1이나 2), kind, payload 길이, 헤더 길이(22 + N), 키 확인값이다. 필드 이름과 타입은 패키지 README에 있다.

## test-vectors

저장소 루트 `test-vectors/`는 시험 파일과 기대 결과다. 다른 언어 구현이 같은 결과를 내는지 확인하는 데 쓴다. 예를 들어 서버가 헤더를 직접 읽는 구현이 이 디렉터리로 검증한다.

- 이 문서가 규칙을 소유하고 `test-vectors/`는 그 규칙의 사례다. 규칙을 바꾸면 사례도 같은 작업에서 고친다.
- `vectors.json`이 파일마다 `readProjectFileHeader` 결과와 `decodeProjectFile` 결과를 적는다.
- 파일 형식과 다시 만드는 방법은 `test-vectors/README.md`에 있다.
- npm 패키지에는 들어가지 않는다.
- 라이브러리 시험(`packages/projectfile/tests/vectors.test.ts`)이 기대 값과 라이브러리 결과, 생성 결과와 커밋된 파일을 비교한다.
