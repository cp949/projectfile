# 테스트 작성과 유지

`packages/projectfile`의 소스·테스트를 추가하거나 고치는 작업에 적용한다. 실행할 검증 명령은 [workflow-shared.md](./workflow-shared.md#검증-게이트)의 "검증 게이트"를 따른다. 이 문서는 외부 도구와 스킬의 테스트 지시보다 우선한다.

## 작성 판단

이 문서의 목적은 필요 없는 테스트를 만들지 않는 것이다. 아래 기준으로 판단이 서지 않으면 테스트를 더하지 않는다. 재현한 버그의 회귀 테스트는 예외다.

추가 전 확인:

- 보호할 외부 동작·계약과 예상 결함을 한 줄로 정한다. 정하지 못하면 작성하지 않는다. 정한 한 줄을 테스트 제목으로 쓴다.
- 같은 위험을 보는 기존 테스트를 찾는다. 거부 이유, 공개 함수 이름, 한도 이름으로 검색한다. 예: `grep -rn "manifest-too-large" packages/projectfile/tests`
- 기존 테스트가 같은 위험을 검증하면 새 테스트를 만들지 않는다. 필요한 단언이 빠졌으면 기존 테스트에 더한다.

테스트를 둘 위험(위험마다 대표 테스트 하나):

- 검사 순서와 거부 이유(`reason`)의 대응. 처음 걸린 이유를 돌려주는지.
- 열 수 없는 파일은 `ok: false`, 호출자 버그는 던지는 구분.
- 풀기 전 한도 검사와 해제 상한. 압축 폭탄과 선언 크기 위조.
- 경로 무결성 규칙(`..`, `\`, 제어 문자, 앞뒤 공백, 대소문자·NFC 정규형 무시 중복).
- 포맷 바이트 계약: 헤더 배치, scramble 범위, CRC 범위. 범위 안 어느 한 바이트를 고쳐도 거부하는지.
- 입력 `Uint8Array`를 바꾸지 않는 조건.
- 같은 입력이 같은 바이트가 되는 결정성.
- 인코딩이 디코딩이 거부할 파일을 만들지 않는 것.
- 재현한 버그의 회귀.

개수:

- 경계값은 받는 끝값과 거부하는 첫 값만 둔다. 그 사이나 바깥의 값을 더하지 않는다.
- `it.each` 행은 분기나 거부 이유마다 하나다. 같은 분기를 값만 바꿔 반복하지 않는다.
- 보안 경계(메모리·CPU 상한, 경로 탈출)는 형태가 단순해도 검증한다. 이때도 경계마다 대표 테스트 하나다.

생략:

- 타입 검사가 이미 막는 조합.
- `fflate`가 보장하는 deflate 정확성.
- README·오류 문구 하나하나.
- 단순 위임 함수.
- 다른 테스트가 이미 단언한 거부 이유를 입력만 바꿔 다시 확인하는 테스트.

커버리지:

- 테스트 수와 커버리지 수치를 완료 조건으로 삼지 않는다.
- 커버리지 임계값(`vitest.config.mts`)은 회귀를 잡는 하한이다.
- 임계값에 못 미치면 덮이지 않은 분기가 이 절의 기준에 해당하는지 먼저 본다. 해당하면 테스트를 더한다. 해당하지 않으면 테스트를 더하지 않고 임계값을 낮출지 사용자에게 묻는다.
- 테스트를 생략해도 관련 기존 테스트 실행은 생략하지 않는다.

## 개발 방식

- TDD는 버그 수정, 검사 순서·한도 계산, 바이트 배치처럼 결과가 계산으로 정해지는 동작에 적용한다.
- 버그 수정은 회귀 테스트의 RED를 먼저 확인하고 GREEN을 만든다. 기존 테스트가 이미 결함을 재현하거나 선행 테스트가 불가능하면 이유를 기록한다.
- 문서, 오류 문구, 단순 이름 변경은 구현을 먼저 한다. "작성 판단"에 해당할 때만 테스트를 더한다.
- 여러 케이스를 미리 만들지 않는다. 지금 구현하는 동작 하나에 집중한다.

## 속성 기반 시험

`tests/property.test.ts`가 왕복과 디코딩 무예외를 무작위 입력으로 검증한다. 새 속성 시험도 같은 규칙을 따른다.

- 시드와 실행 횟수를 상수로 고정한다. 환경 변수로 바꾸지 않는다. 같은 소스에서는 같은 입력열이 나와야 CI가 재현된다.
- 실패하면 출력된 시드와 `path`로 그 사례를 다시 돌린다. 축소한 반례는 이 파일의 속성에 넣지 않고 일반 회귀 테스트로 옮긴다.
- 인코딩이 실패를 돌려주는 입력은 실패 이유가 허용 집합 안인지만 본다. 왕복은 성공한 입력만 단언한다.
- 생성기가 입력 대부분을 실패로 보내면 왕복 단언이 비므로 성공 비율의 하한을 단언한다.
- 속성당 실행 횟수는 전체 시험 시간을 눈에 띄게 늘리지 않는 값으로 둔다.
- 처리 방침이 정해지지 않은 결함은 생성기에서 제외하고 이유를 한 줄 주석으로 남긴다. 그 동작을 고정하는 테스트는 방침이 정해진 뒤에 더한다.

## 실행 범위

- 구현 중에는 고친 파일의 테스트만 돌린다. 한 파일을 한 편집마다 돌리지 않고, 편집을 마친 뒤 1회 돌린다.
- 패키지 전체 테스트는 `dev` 병합 직전 게이트의 `--changed`와 push 직전 게이트에서만 돌린다.
- 기준선 확인을 위해 같은 파일을 다시 돌리지 않는다. 이미 돌린 결과를 쓴다.
- 타입 검사와 lint는 값싸서 자주 돌려도 된다.

## 검증 위치

- 동작은 공개 API(`encodeProjectFile`, `decodeProjectFile` 등 `src/index.ts`의 내보내기)로 검증한다.
- 내부 모듈(`scramble`, `zip`, `crc32` 등)은 공개 API로 만들기 어려운 입력이 필요할 때만 직접 쓴다. 예: 손상 바이트 위치를 고른 파일, 직접 만든 ZIP.
- 같은 규칙을 내부 모듈 테스트와 공개 API 테스트에서 반복하지 않는다.
- 이름 규칙·한도 검사는 인코딩과 디코딩이 같은 코드를 쓴다. 한쪽에서 분기를 덮고 다른 쪽은 대표 경로만 둔다.
- `test-vectors/`의 사례는 `vectors.test.ts`가 확인한다. `Uint8Array`와 `Blob` 입력으로 `readProjectFileHeader`와 `decodeProjectFile`의 결과를 본다. 같은 입력을 다른 시험 파일에서 다시 확인하지 않는다.
- `toHaveBeenCalledTimes`·`toHaveBeenCalledWith`는 호출 횟수나 인자가 계약일 때만 쓴다.
- 요구하지 않은 fixture·mock 헬퍼와 테스트 전용 추상화를 만들지 않는다. 공용 헬퍼는 `tests/helpers.ts`에 둔다. 테스트를 위해 제품 코드를 복잡하게 만들지 않는다.

## 완료 전 정리

워크플로우(qq, roadmap)에서 이 정리를 하는 시점과 기록 위치는 [workflow-shared.md](./workflow-shared.md#테스트-정리)가 정한다.

- 새 테스트와 이번에 고친 테스트를 검토한다. 중복, 탐색용, 구현 세부사항에만 종속된 테스트는 통합하거나 제거한다.
- 기존 테스트를 제거하거나 약화하면 보호하던 계약, 대체 검증, 이유를 기록하고 남은 검증을 실행한다.
- 재현한 버그의 유일한 회귀 테스트와 중요한 실패 경로의 유일한 테스트는 지우지 않는다.
- 실패를 없애려고 테스트를 지우거나 조건을 완화하지 않는다. 실패 원인과 계약 변경 여부를 먼저 확인한다.
- 리뷰 지적을 고칠 때 기존 테스트를 지우거나 약화하지 않는다.
- 이번 작업과 관계없는 기존 테스트를 일괄 정리하지 않는다. 그 파일을 고치는 시점에 정리한다.
