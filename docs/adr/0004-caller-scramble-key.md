# scramble 키를 사용처가 정하고 헤더에 키 확인값을 둔다

scramble 키는 16바이트 `Uint8Array`다.
기본 키 `DEFAULT_SCRAMBLE_KEY`를 내보낸다. 사용처는 자기 키로 바꿀 수 있다.

- 인코딩은 `scrambleKey` 하나로 봉인한다. 옵션을 생략하면 기본 키다.
- 디코딩은 `scrambleKeys` 목록에서 키를 고른다. 옵션을 생략하면 `[DEFAULT_SCRAMBLE_KEY]`다.
- 헤더가 키에서 만든 키 확인값을 평문으로 적는다. 디코딩은 확인값이 같은 키를 고른다. 없으면 `scramble-key-mismatch`다.

키 길이, 키 확인값의 정의, 목록 규칙, 던지는 경우는 `docs/format.md`의 "scramble 키"에 있다.

## 이유

- 다른 사용처가 자기 키로 쓸 수 있어야 한다. 키가 라이브러리에 고정되면 모든 사용처의 파일이 같은 키로 섞인다.
- 기본 키가 있어 키를 정하지 않은 호출자도 바로 쓴다. 기본 키는 이 포맷용으로 새로 만든 값이다.
- 키 길이는 섞는 알고리즘이 읽는 값의 수에서 나온다. 키를 읽는 방식은 `docs/format.md`의 "scramble 키"에 있다.
- 키 확인값이 있으면 목록에서 맞는 키를 헤더만으로 고른다. 맞는 키가 없는 경우를 `scramble-key-mismatch`로 가른다. 확인값이 없으면 틀린 키로 푼 결과는 `crc-mismatch`나 `zip-corrupt`와 구분되지 않는다.
- 키 확인값은 공개되어도 된다. scramble은 기밀성을 약속하지 않는다(ADR-0006).

## 버린 대안

- 라이브러리 고정 키 하나만 쓴다. 사용처가 자기 키를 쓸 수 없다.
- `scrambleKeys`를 주어도 기본 키를 자동으로 목록에 더한다. 자기 키로 만든 파일만 받으려는 사용처가 기본 키로 만든 파일도 받게 된다. 기본 키도 받으려면 호출자가 목록에 넣는다.

## 결과

- 키를 잃으면 그 키로 만든 파일을 열 수 없다. 키 보관은 호출자 책임이다. README에 키 생성 예가 있다.
- 키를 바꾼 뒤에도 이전 파일을 열려면 디코딩 목록에 이전 키를 남긴다.
