# ZIP 전체를 섞는 포맷 버전 2를 두고 인코딩 옵션으로 고른다

포맷 버전은 scramble하는 범위를 정한다.

- 버전 1: ZIP 메타데이터 범위와 `manifest.json` 본문만 섞는다. 기본값이다.
- 버전 2: ZIP 전체를 섞는다. 헤더 CRC도 ZIP 전체를 본다.
- 인코딩 옵션 `scrambleScope`(`"metadata"`, `"all"`)가 버전을 고른다. 비우면 `"metadata"`다.
- 디코딩은 옵션 없이 헤더 버전을 보고 범위를 정한다. 두 버전을 모두 연다.
- 헤더 배치는 두 버전이 같다. 버전 바이트 값만 다르다.

바이트 배치와 검사 순서는 `docs/format.md`의 "헤더", "scramble", "검사 순서"에 있다.
읽기 구조는 `docs/design/01-디코딩-범위-읽기.md`의 "버전 2 읽기"에 있다.

## 이유

- 버전 1은 섞지 않는 본문에 평문이 남는다. 비 ASCII 텍스트의 stored 블록, asset 원본, ZIP 형식 asset의 시그니처다. 이 평문이 장비의 오탐 대상이 되는 사용처가 있다.
- 디코딩이 범위를 알려면 파일이 범위를 밝혀야 한다. 헤더 22바이트가 모두 쓰이고 있어 필드를 더하면 헤더 길이가 바뀐다. 서버가 직접 파싱하는 구현이 깨진다.
- 이미 있는 버전 바이트에 범위를 싣는다. 헤더 길이와 필드 위치가 그대로다. 버전 1만 아는 디코더는 버전 2 파일을 `unsupported-version`으로 거부한다.
- 기본값을 버전 1로 두어 asset `slice` 구조(ADR-0005)와 읽기 비용을 그대로 유지한다.
- 버전 2의 헤더 CRC는 ZIP 전체를 본다. 본문을 모두 읽어 평문으로 되돌려야 하므로 CRC 계산이 더하는 비용은 읽기 한 번이다. 대신 asset 손상을 열 때 잡는다.

## 버린 대안

- 버전 1의 범위를 전체로 넓힌다. 이미 만든 버전 1 파일을 열 수 없게 된다.
- 헤더에 범위 필드를 더한다. 헤더 길이와 서버 파서가 바뀐다.
- 디코딩 옵션으로 범위를 받는다. 파일이 범위를 밝히지 않아 호출자가 알아야 한다. 틀리면 CRC 불일치로만 드러난다.
- 버전 2에서도 CRC를 메타데이터 범위만 본다. 전체를 섞는데 본문 손상을 잡지 않을 이유가 없다. 디코딩이 asset을 어차피 읽는다.

## 결과

- 버전 2는 ADR-0005의 구조를 쓰지 못한다.
  - 입력의 `slice`가 평문이 아니다. 디코딩이 asset 본문을 `CHUNK_BYTES`씩 읽어 평문으로 되돌린 새 `Blob`을 만든다.
  - 인코딩이 asset을 섞으려고 한 번 더 읽는다.
  - 디코딩이 payload 전체를 읽는다.
- 시간이 늘어난다. Node에서 64 MiB asset 하나를 한 번 잰 값이다.

  | 단계   | 버전 1 | 버전 2 |
  | ------ | ------ | ------ |
  | 인코딩 | 107 ms | 278 ms |
  | 디코딩 | 6 ms   | 332 ms |

  브라우저와 다른 크기는 재지 않았다.

- 버전 1 파일은 계속 열린다. ADR-0002의 "이전 포맷"은 magic이 다른 포맷이고, 버전 1은 이전 포맷이 아니다.
- 읽기 호출 수 상한이 버전별로 다르다. 동시에 진행하는 읽기 수(16개)는 같다.
- 헤더만 읽는 서버 구현은 버전 값 2를 받아야 한다. `test-vectors/`에 버전 2 사례가 있다.
- 기밀성은 약속하지 않는다. 결정은 ADR-0006 그대로다.
