# scramble은 기밀성을 약속하지 않고 암호화를 넣지 않는다

scramble의 목적은 인라인 보안 장비의 오탐을 피하는 것이다.
소스 파일을 그대로 서버에 올리면 장비가 오탐해 차단했다. 일반 ZIP은 장비가 열어 보았다.
수단은 ZIP 메타데이터와 manifest 본문을 섞는 것이다. 압축 도구가 파일 목록을 읽지 못한다.

라이브러리는 기밀성, 변조 방지, 서명을 약속하지 않고 암호화를 넣지 않는다.
기밀성이 필요한 사용처는 `encodeProjectFile`의 출력 `Blob`을 표준 암호(WebCrypto AES-GCM 등)로 감싼다.
복호화한 뒤 `decodeProjectFile`에 넘긴다.
복호화하기 전에 암호문 크기를 `maxProjectFileBytes(limits)`에 암호화 증가분을 더한 값으로 직접 검사한다.
예는 `packages/projectfile/README.md`의 "기밀성"에 있다.

## 이유

- 섞는 규칙과 키가 모두 클라이언트 코드에 있다. 코드를 분석하면 풀 수 있으므로 기밀성을 약속할 수 없다.
- CRC도 클라이언트에서 계산한다. 고쳐 쓴 파일의 CRC를 다시 맞출 수 있어 변조 방지도 약속할 수 없다.
- 출력 `Blob`에 표준 암호를 덧씌우면 포맷을 바꾸지 않고 기밀성을 얻는다. 비용은 "결과"에 있다.
- 암호화를 넣어도 이 라이브러리를 쓸 이유는 남는다. 항목 모델, 경로 무결성 규칙, 풀기 전 한도 검사, kind 확인이다. 그래서 "다른 라이브러리를 쓰라"가 아니라 "출력에 덧씌우라"고 안내한다.
- 암호 알고리즘과 키 관리는 사용처가 고른다. 라이브러리는 받은 것을 인코딩하고 디코딩한다.

## 버린 대안

- 라이브러리에 암호화를 내장한다. 알고리즘과 키 관리를 라이브러리가 정해야 한다.
- scramble 규칙을 강화해 기밀성을 약속한다. 규칙과 키가 클라이언트에 있는 한 풀 수 있다.

## 결과

- 파일 내용이 기밀이면 사용처가 암호화를 직접 적용한다.
- 덧씌운 경로는 ADR-0005의 이점을 잃는다. WebCrypto의 `encrypt`와 `decrypt`는 스트리밍이 없어 입력 전체와 결과가 메모리에 올라간다.
- 암호화한 파일은 `readProjectFileHeader`로 읽을 수 없다. 키가 없는 서버는 헤더 검사(ADR-0003)를 하지 못한다.
- 암호화하지 않은 파일에서 서버는 헤더만 검사하고 내용은 검사하지 않는다. 내용 검사가 필요한 쪽은 디코딩한 뒤 검사한다.
